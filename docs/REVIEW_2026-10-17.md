# REVIEW 2026-10-17: the code map's first audit, at `e21deed`

## How it was done, and what it can and cannot say

`tools/codemap` (README there) joins clangd's call graph (every call with the function it sits in,
the override relations) with libclang's reading of every line's condition and every field's
possible values, and dxc's HLSL; the C++ `Compile()` calls link the shader entries. It writes
`build/codemap/` after every build. Its `redundancy.md` asked the whole tree, under EVERY scene
and ANY command-line flag: what is never reached, what is written twice, what branch can never be
taken, what runs every frame. Standings:

- **map**: the finding stands on the map alone;
- **re-read**: Fable grepped or opened the lines and agrees;
- **done**: acted on today (section 6).

Reach is sound by construction (a call is cut only when a condition holding it is definitely
false, a virtual call reaches the overrides in the classes reached code builds), so "unreached"
errs toward reached. Its blind spots: a call through a pointer the code computes, an entry the OS
calls without the code naming it, code under a disabled `#if`. Section 5 lists the map's own
faults met while testing it; each was fixed before these findings were read.

## 7. The helm bench "hang": a cold build at boot, and the exit that waited on it

`gagame scenes/recipes/helm.json ... --bench` stopped after `[residency] earth.color ... tiles
virtual` for 15+ minutes. Not a deadlock: the process was writing `cache/trees/earth.height.7d553010`
the whole time (6,811 tiles, 428 MB in 11 minutes; the finished haulover height tree holds 25,558).
The chain:

1. `scenes/recipes/*.json` are standalone (`base: ""`) and still carry `streaming.seafloor: true`,
   which merrimack.json turned off on 2026-10-11 ("no fake colours"); so the recipe's colour and
   height trees had identities never built (earth.color.aa8bf7b7, earth.height.7d553010, the
   seafloor relief trees -- all created by that run).
2. A tenant's boot loads its coarsest tiles SYNCHRONOUSLY ("a handful of cache-first tiles",
   Residency.cpp, M7w). The colour root's seafloor relief paints its own fine level and folds up
   (HIERARCHY 4.20), so one coarse tile pulled the whole fine window of the height tree through the
   main thread: about 45 minutes, with nothing logged.
3. Once past the boot, the same cold composition sat inside pool loads, and `ResidencyManager::
   Shutdown` waits for every running load: the process could not exit either.

**Done:** the boot asks the trees only for what they HOLD (`g_tileHeldOnly`, core/TileAddress.h):
a tile that would have to be painted, composed or gated answers "not now", the boot writes 255 (map
says nothing) and the async load paints it -- the honest path the code already had for a failed
tile. A loader that is leaving stops its tree (`g_tileStop`, pointed at the residency manager's
`m_quit` around each load and at HeightTree's `m_stop` around each of its jobs): the composition
answers "not now" and the job leaves. Scoped per loader, not process-wide, because the self-test
shuts managers down and keeps using trees. On a warm cache nothing changes (the haulover_city
frozen still is bit-identical); the helm run now passes boot and finishes its frames.

**The disk.** That fixed helm run also composed the cold trees and solved two storm wave fields
(2 x 610 MB in `cache/wave`), ~2.1 GB in all, and D: (the cache's drive) reached 0 bytes free. With
D: full every tile write fails, which is what the self-test's `[rastertest]` identity index and
`[threadtest]` publish race then reported (400 of 400 writes lost). The owner cleared harvest
leftovers on D: (intermediates of the planet OSM chain and superseded building trees); with room
again the self-test exits 0 with the same 37 PASS (only `[scene]`'s count moved, 1024 -> 846, finding
12).

The documented timing instrument (`--sea --headless --rail-flood <dir> --bench --gpu-time --storm
3.0,10,95 --start 2026-08-28T19:30:00`, today merrimack.json with seafloor off and warm trees, 1200
frames). One take before, one after (the gating rule); the noise between two takes of a bracket was
measured by a probe run in between (the bank list read 1.86 ms there against 2.27).

1. **The bench measured a cost no player pays (FrameLoop.cpp, F13's `waveBlock`).** A rail solved the
   wave field ON the frame even under `--bench`, which captures nothing: ONE frame blocked 24,251 ms
   on the storm field's first solve, and spread over 1200 frames it was 20 of the 45 ms mean. `--bench`
   now takes the player's path (the solve runs behind the frame). This changes the instrument, not
   the game: say it before anyone reads 45 -> 25 as a speed-up.
2. **The water bank's tile list: each ring corner asked once (WaterBankLayer.cpp).** A probe split the
   list: `CornerParams` -- the atlas's tide level (a harmonic sum) and the bed read -- was 1.47 of its
   1.86 ms, asked four times a tile; a ring's 4 x 4 tiles share a 5 x 5 lattice, so up to 64 asks did
   25 asks' work, at positions a float's rounding apart. Now each lattice point is asked once a frame.
   **-1.3 ms a frame** on the flight, -1.2 at the helm, a real CPU saving inside RenderFrame. The
   haulover_city frozen still is bit-identical.

Where the frame still goes (after): GPU-bound render 19-20 ms; on the CPU the residency turn 4.5 ms
(the order 1.3, ring memcpy + CopyTiles 1.2, map from held 0.8, UpdateTileMappings 0.7), SetView 3.0
ms (its leaf emit 2.0: 34,775 Want touches a frame, 67 % already tracked), PredictWants 1.0. Those are
the next places to measure; `redundancy.md` section 5 lists what allocates inside them.
